# Part 1 Pain Points

This table records what part 1 costs in human effort (writing SQL by hand without dbt), and what dbt does instead. The last two columns show dbt's solution and the underlying feature.

| Exercise | The problem you hit doing it by hand | What dbt does about it | The dbt feature that does it |
|----------|-------------------|------------|-------------|
| **1. The renumber problem** | You need a new model that must run between 03 and 04. Create `part1_by_hand/sql/03a_cleaned_currency_rates.sql` with `select upper(trim(currency)) as currency, rate_to_usd, rate_date from raw.currency_exchange_rates`. Then edit `05_orders_converted_to_usd.sql` to join on `built_by_hand.cleaned_currency_rates` instead of `raw.currency_exchange_rates`. What do you have to do to the other filenames? | No renumbering. Create `cleaned_currency_rates.sql`, update `orders_converted_to_usd.sql` to use `{{ ref('cleaned_currency_rates') }}`, run `dbt build`. dbt compiles the graph from refs. | Dependency graph derived from SQL, not filenames |
| **2. The rename** | Rename `customer_id` to `cust_id` in `03_cleaned_customers.sql`. Before running, predict which files will break. Then run `./part1_by_hand/run.sh` and count how many files you had to fix. Did `grep customer_id part1_by_hand/sql/*.sql` find them all? (It finds all three hits, but two are false positives in comments and a join condition that references a different table.) | Rename in `cleaned_customers.sql`, run `dbt build`. The view is created successfully. Then the column's tests fail immediately with `Binder Error: Referenced column "customer_id" not found in FROM clause! Candidate bindings: "cust_id", "country"` and the error names `models/staging/schema.yml`. Build stops at PASS=6 ERROR=3 SKIP=4. The 4 skipped nodes are all downstream models (all_orders_combined, orders_converted_to_usd, revenue_per_day) and the parity test, so the mart is never written with bad data. Contrast with part 1: `./run.sh` half-updates schema `built_by_hand` before failing on file 05, reports which file broke but gives no indication of what else is affected, and you manually rerun files 03-06 after fixing them. | Schema tests run before downstream models, skipping everything that depends on the failed test's model |
| **3. Which do I rerun** | You changed `02_cleaned_shopify_orders.sql`. Which of the six files must you rerun to propagate the change? How do you know? | 5 nodes: `dbt ls --select cleaned_shopify_orders+` returns cleaned_shopify_orders, all_orders_combined, orders_converted_to_usd, revenue_per_day, and assert_parity. Then `dbt build --select cleaned_shopify_orders+` runs only those. | Selection syntax (`+`) queries the DAG |
| **4. The silent wrong number** | Run `uv run python generate/gen.py --dirty-currency && ./part1_by_hand/run.sh`. Then check the revenue total again. It is lower than the baseline and every file reported success. Why did rows drop? What would have had to exist for this to fail loudly instead? | `accepted_values` test fails with "Got 8 results, configured to fail if != 0" (8 distinct bad currency values affecting 100 rows, because the test reports distinct values rather than row counts). Build stops. Marts never run. No wrong revenue number ever exists. | Schema tests run before downstream models |
| **5. The missing rows** | Run `uv run python generate/gen.py --late-shopify`. 81 rows out of 20,000 Shopify orders are dropped (the most recent 3 hours). Part 1 reports success on all six files. Part 2 `dbt build` passes all tests including `assert_parity` (13/13), because both pipelines lose exactly the same 81 rows so they still agree with each other. Why does nothing catch it? | Neither stage catches it. Schema tests inspect rows that exist, not rows that never arrived, and the parity test only confirms the two stages agree. What does catch this: a human comparing the aggregate (31950804.04 with the flag vs. 31987050.73 baseline) against the known good number recorded in LOG.md. Nothing in this repo automates that comparison. `dbt source freshness` cannot detect this: `_loaded_at` is constant for all rows so `max(_loaded_at)` is identical with or without the flag, and `BASE` in `gen.py` is fixed in the past for reproducibility, so freshness always reports ERROR STALE even on clean data. | Manual baseline comparison (no dbt feature solves this automatically) |
| **6. The null customer** | Run `uv run python generate/gen.py --null-customer && ./part1_by_hand/run.sh`. Part 1 completes successfully with no errors, but 10 Salesforce orders now reference nonexistent customer IDs (pointing at customer_id values like 14000, 19000, far beyond the 5000 real customers). Check the revenue total: it is correct, so the damage is silent. The orphaned orders contributed their amounts, and nothing complained. | Run `uv run python generate/gen.py --null-customer && cd part2_with_dbt && DBT_PROFILES_DIR=. uv run dbt build`. The `relationships` test fails immediately with "Got 10 results, configured to fail if != 0", the build stops at PASS=8 ERROR=1 SKIP=4, and all four downstream nodes (all_orders_combined, orders_converted_to_usd, revenue_per_day, assert_parity) are skipped. The revenue mart is never written. Contrast with part 1: the referential integrity hole is silent, the revenue number happens to be correct (the orphaned orders' amounts are valid), and you discover the problem only if you manually join customers to orders and notice the 10 NULLs. dbt's `relationships` test makes referential integrity failures loud and immediate. | Relationships test enforces foreign key constraints declaratively |

**Note:** Part 2 models deliberately preserve the `breaks if:` comment blocks from part 1 so the diff between the two stages stays minimal and focused on dbt's syntax (`ref()`, `source()`). Those comments are now dead information in part 2, since dbt derives the dependency graph and breakage automatically.

Run the exercises to see how dbt's features solve each problem.
